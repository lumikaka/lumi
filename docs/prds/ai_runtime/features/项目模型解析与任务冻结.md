# AI 运行时 — 项目模型解析与任务冻结

## overview

该 Feature 让单机项目可以在一个入口查看并覆盖不同 AI 场景的模型，同时保证每个已创建的执行资源不受后续配置变化影响。

文本模型解析优先级为：

1. 当前请求的显式 Provider/模型；
2. `chat_area`、`story_text` 或 `section_premise_selection` 场景覆盖；
3. `project_text` 覆盖；
4. active 且 ready Provider 的全局默认文本模型。

图片模型解析优先级为：显式选择 → `project_image` 覆盖 → 全局默认图片模型。显式只给 Provider 时使用该 Provider 的对应默认模型；显式只给模型时优先在当前有效 Provider 中匹配，再在 ready 选项中匹配。

读取模型设置同时返回 `override`、`inherited`、`effective`、`source` 和 `override_status`。失效覆盖不会阻断页面读取：保留 `override` 供用户修复，`effective` 回退到继承选择；没有任何可用继承时执行返回 `project_model_unavailable`。

保存使用 revision 乐观锁。只能选择当前 ready 且能力类型匹配的模型；文本模型不能写入图片场景，反之亦然。任务创建、Chat、YOLO 和漫画图片 Workflow 保存解析三元组；重试、多步派生和内部创建的同一 Workflow thread 都沿用该三元组。

## data_model

`project_model_settings` 保存五个场景的可空覆盖对与 revision。执行表保存非空 `provider_uuid`、`model` 和 `model_source`，历史记录不会随设置更新。

对外设置结构：

- `revision` — 当前乐观锁版本
- `settings` — 以五个场景 key 索引；每项含 `kind`、`override`、`inherited`、`effective`、`source`、`override_status`
- `options.text_models` / `options.image_models` — 每项只含公开 Provider UUID、类型、名称、模型、能力 kind、ready 和 active 状态

`override_status` 为 `inherit`、`valid` 或 `invalid`。选择结构只含 `provider_uuid` 和 `model`。

## api

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v1/projects/:project_uuid/model-settings` | GET | 返回 revision、五个场景的继承/有效选择和可用 text/image 选项。 |
| `/api/v1/projects/:project_uuid/model-settings` | PATCH | 接收 `expected_revision` 与 `overrides`；值为 `{provider_uuid, model}` 时覆盖，为 `null` 时恢复继承。 |

所有响应遵守统一 JSON 信封，字段使用 `snake_case`。revision 冲突返回 `project_model_settings_conflict`；未知场景、不可用模型、UUID 或能力类型错误返回 `project_model_settings_invalid`。API 不接受或返回 Provider 内部 ID。

创建业务任务的既有 API 可以显式传 Provider/模型，也可以留空走解析器；其返回 Task、Chat、Run 或 Workflow 时包含冻结后的 `provider_uuid`、`model` 和 `model_source`，方便审计。

## ui

| 页面 / 入口 | 说明 |
|---|---|
| `/projects/:project_uuid/overview/summary` 的项目模型卡片 | 分别展示项目文本、项目图片、Chat、Story 与 Section Premise 选择；每个下拉包含“继承”及能力匹配的 ready 模型。 |
| 项目模型卡片状态 | 显示当前来源与有效模型；失效覆盖给出修复提示，保存期间禁用重复操作，revision 冲突后刷新事实源。 |

## others

数据库 migration 必须成对维护 `project_model_settings` 和五张执行表的 `model_source`。新增 AI 场景必须先声明 text/image 能力、继承父级和稳定 source 值，再接入任务创建点；不能在 worker 开始执行或重试时重新解析当前设置。

测试至少覆盖五个场景继承、覆盖清除、Provider 失效回退、能力类型错误、revision 冲突、显式选择、Task/Production/Chat/YOLO/Workflow 冻结，以及设置变化后的重试一致性。
