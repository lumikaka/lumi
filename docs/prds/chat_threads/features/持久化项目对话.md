# 对话线程 — 持久化项目对话

## overview

该 Feature 提供可恢复的项目 Agent 对话。普通首次提交创建 `conversation` Thread 和首个 Turn；首页对话式项目创建则把原始输入、Thread、首个 Turn/Run/Item、队列 Job 与唯一 bootstrap 在一个项目库事务中恰好一次提交。执行过程把 Run、消息 Item、工具与事件持久化。Chat Tool 可以发起异步 Workflow，在不创建影子 Thread、不占用 Agent worker 的情况下等待终态并继续同一 Run。页面可以分页浏览线程、cursor 回溯消息和事件，并在重新打开、重连或窗口重新聚焦时从 REST 重建状态。

## data_model

Thread 固定 `project_id`、`thread_type=conversation|workflow`、标题、状态和冻结模型，不保存 `scope`、`scene` 或 `subject_uuid`。Turn 按 queue sequence 排队，Run 保存一次执行，Item 按 Thread 内 sequence 排列；用户输入 Item 可拥有接收时的冻结 Reference，成功图片写回的 Tool Result 可拥有服务端生成的更新后 Reference，`chat_events` 仅追加，不允许把实时 payload 作为历史来源。

`project_creation_bootstraps` 以唯一 `creation_session_uuid` 关联应用库创建 Saga，并以 bigint `thread_id`、`turn_id` 关联同库 Chat 记录。它与首轮所有记录、River Job 共用事务，因此任何 Thread、Turn、Run 或 Job 注入失败都不会留下部分首轮；重试读取该记录返回原公开 UUID。

一个用户 Turn 始终恢复同一个 Run，内部可跨越大量模型请求、工具调用、用户输入等待、Workflow 等待和多次增量上下文压缩；不会因旧步骤数自动创建 continuation Turn。`POST .../turns` 仅为旧客户端兼容继续解码 `max_steps`，服务端明确忽略该字段，客户端和新文档不发送或展示它。运行时固定预算只作为内部安全边界，达到后最多执行一次无工具最终说明请求，并在原 Turn 内完成或以 `agent_turn_budget_exceeded` 失败。

上下文大小按发送给 Chat Completions 的消息和 Tool 定义共同计算：384 KiB 开始压缩、目标低于 256 KiB、512 KiB 为硬上限。压缩增量合并最新本地摘要，不额外调用模型；当前 Turn 初始输入、Steering、用户回答和最新完整 Tool 批次保持原文，Tool Call/Result 作为原子批次处理，原始 Item 永不删除。

异步 Workflow 等待使用 `workflow_awaits` 持久关联当前 Turn、Run 与 Tool Execution。受历史表 CHECK 约束，底层 Turn/Run 等待时仍为 `in_progress`，Turn REST DTO 显示 `waiting_for_workflow`；await 终态事务再把有效父 Turn/Run 改为 `queued` 并插入唯一 `JobChatResume`。

## api

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v1/projects/:project_uuid/chat_threads` | GET / POST | 页码读取或创建通用 Thread；创建不接受业务场景或 subject。 |
| `/api/v1/projects/:project_uuid/chat_threads/:thread_uuid` | GET | 读取单个 Thread。 |
| `/api/v1/projects/:project_uuid/chat_threads/:thread_uuid/turns` | GET / POST | 读取 Turn（含 `waiting_for_workflow` 投影），或用 `input_text` 与最多 16 个 `references` 创建用户输入。 |
| `/api/v1/projects/:project_uuid/chat_threads/:thread_uuid/items?before=&after=&limit=` | GET | cursor 读取对话 Item。 |
| `/api/v1/projects/:project_uuid/chat_threads/:thread_uuid/events?after=&limit=` | GET | cursor 读取脱敏事件流。 |

## ui

| 页面 / 入口 | 说明 |
|---|---|
| 项目 ChatArea | 线程列表、草稿对话、按 Turn 分组的消息流和状态恢复；URL 中的 `chat_thread_uuid` 自动选中 bootstrap Thread 并在桌面展开或窄屏覆盖显示。inline Workflow 根据 `origin_turn_uuid` 显示在发起 Tool Call 的 Turn 内，同一 Turn 支持多个卡片并按创建时间、UUID 稳定排序。 |

## others

列表使用页码分页，Item 与 Event 使用 opaque cursor。User Item 和拥有服务端写回快照的 Tool Result 返回 `references`，不返回旧 `upload_uuids` 或 `image_references` 合约。客户端收到带公开 Thread/Workflow/Turn UUID 的 `chat:*` 或 `workflow:*` 变更提示后失效相应查询，并在首次 join、重新 join 与窗口重新聚焦时 REST 校准；不定时 HTTP 轮询。

项目 `setup_status=draft` 时，Chat 本身与 `request_user_input`、文档读取和 Project Setup reviewed routes 保持可用；其他写 API、Workflow 和 image 工具在执行层失败关闭。System Context 每次模型循环注入最新公开 `setup_status`，不依赖首次 Run 的缓存。

首页 bootstrap 的首个 Turn 在项目变为 `ready` 后仍由 `project_creation_bootstraps.turn_id` 识别：它只允许只读、可信运行时 finalization 恢复和绑定该成功定稿证据的 YOLO 创建，其他写操作与 `image_gen` 失败关闭。该 bootstrap finalization 免确认，普通危险操作仍使用全局确认。YOLO 创建时建立唯一 `workflow_awaits` 并在来源 Turn 内展示；终态 Tool Result 恢复同一 Run 后，模型输出一次最终说明。同一 Thread 的后续 Turn 不继承门禁。

等待 Workflow 的 Turn 仍允许停止或排队 Follow-up，但不能立即 steering：停止会在同一父链路中取消 Run、await 并向该 Tool Call 独占创建的 Workflow 发出取消请求；单独取消 Workflow 会以 cancelled Tool Result 恢复仍有效的父 Run。Workflow 失败同样作为结构化 Tool Result 交给模型解释，不直接把父 Run 归类为 Provider failure。
